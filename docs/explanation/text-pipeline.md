# Text pipeline behavior (chunking, summaries, assets)

This page documents both text-pipeline execution modes: the real LLM-backed `podcast draft` flow and the deterministic
stub flow used for local smoke tests.

## Pipeline stages (current)

1. Chunk transcript text into overlapping segments.
2. Summarize each chunk and roll up an episode summary.
3. Generate draft candidate assets from the episode summary.

`podcast draft` runs all three stages. In its default mode, it invokes the configured local drafter CLI once per
summary or candidate request and validates the returned JSON. It can create a workspace from `--transcript` or reuse an
existing workspace and transcript. Host names from `--host` or `episode.yaml` are included in the prompts.

`podcast draft --dry-run` uses the stub implementations for deterministic, agent-free output. The lower-level
`podcast summarize --dry-run` and `podcast draft-candidates` commands expose the same stub stages individually.

## Chunking behavior

Chunking is implemented in `podcast_pipeline.transcript_chunker` and writes a `.txt` file plus a metadata JSON file per chunk.

- Tokenization: whitespace-delimited tokens matched by `\S+`.
- Chunk IDs: start at 1 and increment per chunk.
- Default config: `ChunkerConfig(max_tokens=1200, overlap_tokens=200, boundary_lookback_tokens=200, min_tokens=None)`.
- All four settings require actual integers (booleans, floats and nonfinite numbers are refused before processing).
  Only `min_tokens` may be `None`; existing positive-size and overlap range relationships still apply.
- Effective minimum size: when `min_tokens` is `None`, `effective_min_tokens` is 60 percent of `max_tokens`.
- Boundary selection:
  - Prefer paragraph boundaries (`\n\n`), then sentence boundaries (`.`/`!`/`?` followed by whitespace), then line boundaries (`\n`).
  - Sentence punctuation may be followed by any combination of ASCII closing quotes (`"`, `'`), parentheses (`)`),
    or square brackets (`]`) before the whitespace. Bare punctuation also counts.
  - Search backward up to `boundary_lookback_tokens` from the desired end.
  - If no boundary is found, cut at `max_tokens`.
- Overlap: next chunk starts at `end_token - overlap_tokens` (unless that would go backwards).

Chunk outputs live under `transcript/chunks/`:

- Text: `chunk_0001.txt`
- Metadata: `chunk_0001.json` containing `chunk_id` and `text_relpath` (time fields are not populated yet)

`ChunkerLimits` defaults to 8 MiB of coherent regular UTF-8 source, 500,000 whitespace tokens,
4096 chunks and 32 MiB of aggregate UTF-8 chunk text (including overlap and added newlines).
Token and output capacity is charged before retaining each token/chunk. A refusal raises
`ChunkerResourceError` before any staging or publication, preserving the last completed set.
Discovery and backup recovery use the same envelope, plus 2 MiB for the manifest and 4096 bytes per
metadata file. Once the source digest matches, they count whitespace tokens up to the first token
over the limit. Only chunk generation builds the byte-offset index. Programmatic callers may supply
smaller `limits` to chunking, writing and discovery. Reduce source size or overlap before retrying
a refused transcript.

## LLM-backed summaries

The default `podcast draft` flow uses `podcast_pipeline.summarization_llm`. It renders structured prompts for each
chunk, validates each JSON response, writes chunk summaries, and then renders a roll-up prompt for the episode summary.
The drafter CLI is selected from the workspace or global agent configuration.

Each chunk source must be one coherent regular UTF-8 file of at most 256 KiB (no symlinks/FIFOs).
Actual reads enforce the ceiling and check descriptor/name generations. Each complete rendered
chunk or reduction prompt is capped at 256 KiB of UTF-8, including schemas, host constraints and
all context. Reduction serializes one summary at a time into a bounded compact JSON array, preserving
all values and provenance, instead of building an unlimited aggregate first. An oversized source,
host list or complete prompt raises `SummarizationResourceError` before that runner call and its
artifact publication. Existing artifacts for the refused call stay intact; earlier completed chunk
calls remain cached. Nothing is silently truncated. Split/rechunk excessive source explicitly and
retry; increasing the agent timeout does not raise these limits.

LLM-backed summaries use the same paths as the stub mode:

- Chunk summaries: `summaries/chunks/chunk_0001.summary.json`
- Episode summary: `summaries/episode/episode_summary.json`
- Rendered outputs: `episode_summary.md` and `episode_summary.html`

## Stub summaries

Summaries are generated by `podcast_pipeline.summarization_stub` and written under `summaries/`:

- Chunk summaries: `summaries/chunks/chunk_0001.summary.json`
- Episode summary: `summaries/episode/episode_summary.json`
- Rendered outputs: `episode_summary.md` and `episode_summary.html`

Stub behaviors:

- Chunk `summary_markdown` includes a heading (`## Chunk N`) plus the first non-empty transcript lines.
- `bullets` are derived from early non-empty lines (max 5 by default).
- `entities` are the first capitalized tokens in the chunk (case-sensitive).
- Episode `key_points` and `topics` are unique rollups of chunk bullets and entities.

## LLM-backed asset candidates

The default `podcast draft` flow uses `podcast_pipeline.asset_candidates_llm`. It provides the episode summary,
optional chapters, and host names to the configured drafter CLI and validates the structured candidate response.
Asset candidate prompts admit up to 65,536 characters across summary, key points, topics, chapters and
host names, and up to 200 combined key points, topics, chapter entries and hosts. Chapter entries in
drafts are stripped nonblank lines. Exceeding either limit stops candidate generation before rendering
the prompt or calling the candidate model. Earlier versions silently kept only the first 200 chapter
lines; a longer chapters file now stops the run after summarization instead. The summary is cached, so
shorten the supplemental context and retry.
For per-asset regeneration, `inputs.chapters` is read through nonblocking regular-file and
workspace-directory descriptors. Every path component must stay inside that opened workspace;
symlinks, changed file/directory names, in-place changes, invalid UTF-8, more than 1 MiB or more than
200 physical lines (including blanks) are refused before creating the runner. Admitted chapter
lines keep their order after stripping/blank removal. Shorten an excessive chapter file explicitly;
the former silent first-200-lines truncation is gone. These checks detect observed changes during
the read; they do not lock out manual edits after the read completes.

Generated candidates receive a fresh application UUID, observation timestamp and `llm_drafter` provenance
(`asset_v1` for drafts, `regen_v1` for regeneration); model-supplied identity, date and provenance are discarded.
Historical stored records retain their original metadata.

Titles, Auphonic subtitles and slugs use the same single-line validation as custom selections; slugs must use
lowercase ASCII letters/digits with single hyphens between words. These assets and short summaries are stored
in their natural plain-text format. Invalid text rejects the entire response before any alternative is published,
with a zero-based candidate position and asset name in the error, never its content. Tag post-filtering and
long-form Markdown keep their existing contracts. No invalid slug or multiline title is silently rewritten.

Workspace store reads bind candidate UUID/asset and review iteration/reviewer to the requested artifact path.
Misplaced valid JSON raises `WorkspaceStoreError` and remains untouched for explicit repair; move or restore
the correct record rather than editing IDs to force admission. Legacy optional provenance and unnamed reviews
remain supported when their requested identity matches.

Dashboard candidate deletion backs up that candidate's JSON/renderings, all selection formats for the asset
and state under the workspace lock. Handled unlink or state-publication failures restore the previous bytes
together. A different current selection and unrelated candidates remain intact. If compensation itself fails,
the error names retained sibling backups for manual recovery. This does not cover process death mid-update.

## Stub asset candidates

Asset candidates are generated by `podcast_pipeline.asset_candidates_stub`.

Inputs:

- `summaries/episode/episode_summary.json`
- Optional chapters, resolved in this order:
  1. `--chapters` CLI argument
  2. `episode.yaml` `inputs.chapters`
  3. `transcript/chapters.txt`

Outputs:

- One candidate set per asset kind under `copy/candidates/<asset_id>/`.
- For each candidate: `candidate_<uuid>.json` plus `.md` and `.html` renderings.

Current asset ids (from `AssetKind`):

- `description`
- `shownotes`
- `summary_short`
- `title_detail`
- `title_seo`
- `subtitle_auphonic`
- `slug`
- `cms_tags`
- `audio_tags`
- `itunes_keywords`
- `mastodon`
- `linkedin`
- `youtube_description`

In the LLM mode, the tag assets (`cms_tags`, `audio_tags`, `itunes_keywords`) get house-style tag rules in their
prompt, optional few-shot examples from past episodes (`tags.examples`) and a deterministic post-filter that drops
excluded terms and host names and caps the count. See `reference/configuration.md` ("Tag assets").

Both modes write candidates to the same workspace paths. Every stub asset is Markdown, including the heading-wrapped
slug and tag lists. Descriptions and social copy use key points; titles and slugs use topics. Shownotes use chapter
headings and key points. The stub does not incorporate `summary_markdown` or call an agent.

Stub UUIDs identify workspace-local slots: generator version, asset id and one-based variant. They are stable across
processes and hash seeds, independent of source text, chapters, workspace path, candidate count and creation time.
Changing the generator version changes the IDs and their `stub_asset_generator` provenance references
(`version:NN`). These are not global content IDs: separate episodes can have identical slot IDs, and changed input
can replace the content in an existing slot. The default creation time is fixed at `2000-01-01T00:00:00Z`; callers
of `DraftCandidatesConfig` can supply an explicit timestamp, which is preserved.

`tests/test_asset_candidates_stub.py` covers every asset's semantic markers and format, downstream tag/slug parsing,
slot uniqueness, version changes and reproducibility in separate interpreters with different hash seeds.

### Stub source boundaries

Key points and topics are stripped and blank entries are ignored before rotation, so whitespace-only input now uses
the same fallbacks as empty input instead of producing empty keyword lists or stray `-` tags. The source summary
and chapter sequences are not changed. Duplicate entries retain their positions during rotation; the downstream
tag reader strips and deduplicates tags with case folding, retaining the first spelling. Variants wrap around the
source length, so a singleton can appear twice in a short summary or title. Repeated copy is expected in this stub.

Empty topics use `podcasting` / `automation` for titles, `podcasting-automation` for the slug and
`podcast, audio, automation` for iTunes keywords. CMS/audio tag lists use the `(none)` placeholder. Empty key points
use `A quick tour of the episode.` for descriptions and social copy, the episode title for the subtitle, and
`A new episode is out.` / `We cover practical takeaways.` for short summaries. Stub slugs retain only ASCII a-z,
digits and hyphens, with `episode` as the fallback when no ASCII content survives; Unicode text elsewhere is kept.

Chapter lines are stripped, blanks removed, and the original order retained. Shownotes include the first 12 chapters
as headings, each with up to three rotated key points; without chapters they have a `Notes` section with up to six
key points. Description and YouTube chapter lists include all chapters, or `(no chapters provided)` when empty.
The existing Markdown renderer escapes raw HTML and refuses unsafe link schemes, while retaining supported links,
inline code and punctuation. These rules are exercised from the generator through the production HTML renderer in
`tests/test_asset_candidates_stub_boundaries.py`, alongside empty, whitespace, Unicode and repeated-source cases.

## Complete cached generations

`transcript/chunks/complete.json` version 1 records `source_sha256`, `config`, ordered `chunk_ids`
and a `files` map of text/metadata basenames to SHA-256 digests. Chunks are written in a sibling staging
directory, then the previous directory is moved aside and the completed directory renamed into place.
A handled publication error triggers an attempt to restore the previous directory. Discovery rejects legacy prefixes,
missing or changed members and sets whose source no longer matches `transcript/transcript.txt`.
Discovery and backup recovery also validate each metadata file against the chunk schema. Its
`chunk_id` and workspace-relative `text_relpath` must match its manifest slot and canonical text path,
even when the file matches the recorded digest.
Publication and discovery share the existing stable workspace-directory lock with state/YAML writers.
Staging happens outside the lock; the source is read again under the lock before swapping. Changed
source refuses publication with `ChunkSourceChangedError` (a `ValueError`) and preserves the current set. Swap, rollback and old-set retirement stay
under that lock, so one writer cannot restore over another writer's committed generation and discovery
cannot inspect the inter-rename gap. The dashboard takes the lock for both its manifest count and
bounded legacy directory scan, so status reports the count from one published generation. Transcript
ingestion uses the same lock for invalidation and swap.
`EpisodeWorkspaceStore.publication_lock()` exposes this boundary for other artifact readers; do not
reacquire it or call state/YAML writers inside it. Discovery returns a snapshot, not a lease across
later agent calls; this does not serialize entire draft jobs or exclude manual filesystem edits.

`summaries/episode/complete.json` version 1 records `chunks_sha256` (the chunk manifest digest)
and `files` digests for JSON, Markdown and HTML. All outputs are rendered before publication;
individual files use atomic replacement and the completion marker is written last. Handled write
failures restore the previous files and their permissions. If recovery itself fails, remaining files
are still restored where possible. File restores use a staged copy and sync the containing directory
before retiring the sibling backup. If recovery cannot confirm the restore, the error identifies
retained backups for manual repair. A summary JSON alone is never a reusable completed generation.
Draft resume requires each file to be regular and stable during its read. The summary
marker is limited to 4 KiB and parsed as strict JSON. Verification streams the SHA-256 digests within
2 MiB for the chunk manifest, 32 MiB for summary Markdown and 64 MiB for HTML. It takes a bounded
snapshot of the summary JSON (up to 64 MiB) and verifies its digest. The larger JSON and HTML
budgets allow for escaping and formatting. Candidate generation uses the model parsed from those
verified JSON bytes. Rerun draft to rebuild summaries whose files or model fail validation.
Explicit contradictory LLM chunk identities are rejected;
omitted identities are supplied from the request. Each validated chunk summary is fully serialized,
then written to a unique sibling temporary file, flushed/synced and atomically replaced. Partial-write,
flush, sync, replacement and catchable interruption failures before replacement keep the previous
chunk cache bytes intact and remove the temporary file. Retry can regenerate that chunk; a surviving
chunk alone still does not certify a complete episode summary generation.

These are local recovery boundaries, not multi-file atomic transactions or cross-process draft scheduling.
If process death between directory renames leaves `transcript/chunks` absent, discovery and writers
recover under the workspace lock, before attempting new staging. Exactly one `.chunks-previous-*`
directory must remain, with a complete, bounded manifest/file set matching the canonical transcript.
Its recorded configuration is validated but need not match the new request; normal reuse admission
then decides whether it needs rebuilding. Staging directories (`.chunks-*` without `previous-`) are
never promoted. Complete empty generations can also be recovered.

Multiple backups, damaged files or a changed/missing source raise `ChunkRecoveryError` and retain
all evidence (`podcast draft` prints it as `Error: ...` and exits with code 1, as it does for
`ChunkerResourceError` and `ChunkSourceChangedError`). Inspect the manifests, hashes and canonical transcript; deliberately move unrelated
backups out of the `.chunks-previous-*` namespace, restore the intended source/backup, then retry.
Do not delete backups just to suppress an ambiguous outcome. An existing canonical directory remains
authoritative; this rule does not replace it with an older backup. The deterministic dry-run golden
fixture includes both manifests; failure fixtures use invented transcript and summary text.

If installing the new directory fails and the immediate restore rename also fails, the original
publication error propagates with a note naming the restore failure and the retained backup path.
The previous generation remains available for validation and recovery.

Installing the completed directory is the commit point. An `OSError` retiring its old backup
afterward attempts one warning naming the retained path. The new generation's metadata is returned
even if a logging handler fails. Discovery continues to identify the new canonical set. Check the
published generation before retrying work after a cleanup warning. Later publishers retire only
their own backups. To clean retained evidence, stop draft/transcription writers, verify the canonical set with
`discover_complete_chunk_ids(layout, config=requested_config)`, and inspect/move or remove only
the named old backup under `publication_lock()` (discovery must run outside that lock).
Ingesting a new transcript (`podcast draft --transcript`) retires every `.chunks-previous-*`
backup under the same lock, before it removes the canonical set and summaries: those backups were
built from the replaced source and could otherwise be mistaken for an interrupted swap. If that
removal fails, ingestion stops before the canonical set or transcript changes.
Keep ambiguous evidence for reconciliation if the canonical directory is absent. A cleanup warning
does not roll back the committed set; prepublication and swap failures still fail and preserve or
restore the previous set.

Draft reuse requires all four requested chunker settings to match the manifest's validated configuration,
as well as a supported version and source identity. Changing any setting rebuilds the chunks through
the complete-set publication path. The changed manifest digest invalidates the episode summary;
all chunk summaries and the episode summary are regenerated before candidate calls, so no summary
from the incompatible configuration reaches drafting. Unchanged configurations reuse completed summaries.
